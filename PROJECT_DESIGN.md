# Project Design: MetalTech production scheduling as a QUBO

This document describes the data model, the QUBO formulation, the qubit-reduction methods and the
solvers. Code references point into `erpq/`. Numbers quoted here come from `results/` and are
regenerated by `run_baseline.py` and `run_extension.py`.

---

## 1. The optimisation problem

**Input.** A set of jobs $J$ (parts Z1, Z2, ...). Job $j$ is a chain of operations
$o_{j,0} \to o_{j,1} \to \dots$. Each operation $o$ has an integer duration $p_o$ (hours) and needs one
machine of type $m(o) \in \{T, F, S\}$. In the baseline every job has the route $T \to F \to S$
($T \to F$ for instance A) and there is one machine per type.

**Decision.** For every operation a start time $s_o \in \mathbb{Z}_{\ge 0}$ (and, with parallel
machines, a unit $u_o$).

**Constraints.**
1. every operation starts exactly once and runs without interruption ($e_o = s_o + p_o$);
2. technological order inside a job: $s_{o'} \ge s_o + p_o$ for consecutive $o \to o'$;
3. machine capacity: two operations on the same unit never overlap.

**Objective (baseline).** Minimise the makespan $C_{\max} = \max_o e_o$.

This is the flow-shop special case of the job-shop problem ($F3\,\|\,C_{\max}$, NP-hard for three or
more machines). For two and three machines a permutation schedule is optimal. We use this as an
*independent* check (`heuristics.brute_force_permutations`) and for the job-order code of Section 5.6,
which is a comparison only. The time-indexed QUBO does not assume it, so it also covers job shops
(Stage 2).

**Reference values.** Instance A: lower bound 4, optimum 4 (FIFO plan: 5). Instance B: lower bound 8,
optimum 8. Both are confirmed by brute force over all permutations and by CP-SAT (`erpq/classical.py`).

### Extended model (Stage 2)

The same data model (`erpq/model.py`, a backwards-compatible JSON schema) adds:

| feature | data | constraint / objective | effect on the time-indexed QUBO |
|---|---|---|---|
| per-job routes (job shop) | order of `operations` | precedence chain per job | none: precedence is already per job |
| due dates and weights | `due_date`, `weight` | objective $a\,C_{\max} + b\sum_j w_j\max(0, C_j - d_j)$ | tardiness is a **linear** term; makespan needs $H - LB$ thermometer qubits |
| sequence-dependent setups | job `family`, `setup_times[type][f][g]` | gap $s_b \ge e_a + \sigma_{ab}$ between consecutive jobs on a unit | more quadratic terms (wider conflict window); 0 extra qubits |
| maintenance / breakdowns | `unavailability` windows per unit | no operation overlaps a window | **removes** variables (window level and above; at the unpruned levels: a linear penalty per forbidden start) |
| release dates, machine ready times | `release`, `machine_ready` | earliest starts | **removes** variables (as above) |
| rolling state | `time_origin`, `fixed` (running operations) | nothing before "now"; running ops block their unit | **removes** variables (as above) |
| parallel machines | `machines: [{id, type}]` | each operation picks one unit of its type | variables $\times$ number of units |

The objective used in Stage 2, $2\,C_{\max} + \sum_j w_j T_j$, can be read as cost units: 2 per
hour of shop overtime, $w_j$ per hour that order $j$ is late.

## 2. Data model of the QUBO: the state and its variables

**State.** A state is a *start-time assignment*: for every operation, the hour (and unit) at which it
starts.

**Variables.** One binary variable per admissible (operation, unit, start time):

$$x_{o,u,t} = 1 \iff \text{operation } o \text{ starts at hour } t \text{ on unit } u .$$

**Parameter: the horizon $H$.** All operations must end by $H$, so $t \in [0, H - p_o]$ at most.
$H$ trades size against safety: a larger $H$ means more qubits, while an $H$ below the optimal makespan
makes the problem infeasible. We choose $H$ in two ways:

* **Baseline:** $H$ = makespan of the FIFO plan (what the ERP does without optimisation). This is a
  valid upper bound, so the optimum is always representable, and the QUBO has to improve on the ERP's
  plan: for instance A, $H=5$ while the optimum is 4. For instance B the FIFO plan already gives
  $H = 8$, the reference horizon of the challenge.
* **Stage 2: horizon ascent** (`erpq/horizon.py`). Start at the lower bound $LB$ and increase $H$.
  Horizons that constraint propagation proves infeasible cost no quantum call. Stop when the
  *horizon certificate* holds (Section 5.4).
* **Random-instance studies (scaling, investment): shift horizon** $H = C^*_{\max} + 1$, i.e. "all
  work must be finished by the end of the shift". The QUBO is exact for this model and CP-SAT with the
  same horizon is the reference. We chose this because with tight random due dates the global
  certificate can need very long horizons (180+ qubits), which would measure the horizon rule rather
  than the solvers.

**Why time-indexed?** Every constraint of the problem, including setups, maintenance windows, release
dates and parallel machines, becomes a sum of pairwise products or a removed variable. No slack
variables are needed, and the objective is exact. Alternatives we considered are listed in Section 9.

## 3. The QUBO

$$E(x) \;=\; A\sum_{o}\Big(\sum_{u,t} x_{o,u,t} - 1\Big)^2
\;+\; B\!\!\sum_{(o\to o')}\sum_{t' < t + p_o}\!\! x_{o,u,t}\,x_{o',u',t'}
\;+\; C\!\!\sum_{\substack{a,b \text{ different jobs}\\ \text{same unit } u}}\sum_{\text{clash}(t,t')}\!\! x_{a,u,t}\,x_{b,u,t'}
\;+\; \text{Obj}(x)$$

(`erpq/timeindexed.py:build_time_indexed_qubo`)

| term | linear part | quadratic part | meaning |
|---|---|---|---|
| one-hot | $-A$ on every $x_{o,\cdot}$ (+ constant $A$) | $+2A$ between two start options of the **same** operation | each operation starts exactly once |
| precedence | - | $+B$ between start $t$ of $o$ and start $t' < t + p_o$ of its successor | job order $T \to F \to S$ |
| capacity | - | $+C$ between two operations of different jobs on the same unit whose intervals (plus setup gap) clash: not ($t' \ge t + p_a + \sigma_{ab}$ or $t \ge t' + p_b + \sigma_{ba}$) | one operation at a time; changeovers |
| makespan, "exp" | $c(e)$ on the last operation of each job, $c(e)=0$ for $e \le LB$, $c(e) = (n+1)^{e-LB-1}$ above | - | lexicographically exact $\min C_{\max}$ without extra qubits |
| makespan, "thermometer" | $+a$ on $z_T$, $+D$ on $x_{o,u,t}$ with end $> T$ | $-D\,x_{o,u,t}\,z_T$ | $C_{\max} = LB + \sum_T z_T$, exact as a linear term |
| tardiness | $b\,w_j \max(0, t + p_o - d_j)$ on the last operation of job $j$ | - | weighted lateness |

**Variable interactions.** Variables of the same operation interact through the one-hot term.
Variables of different operations interact only if the operations are consecutive in a job or share a
machine type. Operations of different jobs on different machines are independent. The interaction graph is
sparse: 181 quadratic terms for the 39-variable 3x3 QUBO, 123 for the 33-variable one.

**The exact makespan with exponential weights.** With $n$ last operations, a schedule with
$C_{\max} = LB + k$ costs at least $(n+1)^{k-1}$. A schedule with $C_{\max} = LB + k - 1$ costs at most
$n(n+1)^{k-2} < (n+1)^{k-1}$. So minimising the sum minimises $C_{\max}$ first, and the dynamic
range stays small for a tight $H$: 1, 4, 16, ... For weighted objectives we use the thermometer
encoding instead (an "or" over the last operations, written as pairwise penalties).

### 3.1 Penalty weights and the correctness theorem

All penalty terms are non-negative, are $0$ exactly on feasible schedules, and are $\ge$ their weight
otherwise (a one-hot group with 0 or $\ge 2$ ones contributes $\ge A$). All objective terms are
non-negative. Let $U$ be the objective energy of any known feasible schedule inside the domains. We use
the FIFO plan if it fits the domains, else the best heuristic schedule (NEH / EDD), else an analytic
bound: the worst objective inside the domains. For metaltech_monday at $H^* = 9$, both heuristics end
after 9, so $U = 16$ comes from the bound and the penalties are 17.

> **Theorem.** If $A, B, C, D > U$, every ground state of $E$ is a feasible schedule with optimal
> objective (within the horizon).
>
> *Proof.* A feasible optimum $x^*$ has $E(x^*) = \text{Obj}(x^*) \le U$. Any infeasible $x$ violates
> at least one penalty term, so $E(x) \ge \min(A,B,C,D) > U \ge E(x^*)$. Among feasible states
> $E = \text{Obj}$, which is exact (or lexicographically exact for the "exp" encoding). $\square$

We therefore set **all penalties to $U + 1$** (`penalty=None`). For instance B at $H = 8 = LB$, $U = 0$,
so the penalties are 1 and the QUBO is a pure feasibility problem: every zero-energy state is an
optimal schedule. For instance A at $H = 5$, $U = 1$ (the FIFO plan ends at 5), so the penalties are 2.
Small penalties keep the energy landscape well conditioned for QAOA and annealing. The penalty sweep
on `metaltech_monday` (`results/extension/algorithms.md`) shows the trade-off: U + 1 = 17 is provably
sufficient. 0.25x and 0.5x of it still happen to keep the optimal ground state, and SA does best at
0.5x (0.61 success per read vs 0.43). Larger penalties (2x, 4x) lower both SA (0.29, 0.26) and QAOA.
We keep the *provable* U + 1 as the default; a tighter U from a better heuristic directly helps the
solvers.

**Feasibility condition.** The QUBO has a zero-penalty state iff some schedule ends by $H$. This holds
whenever $H \ge C^*_{\max}$, guaranteed by $H \ge$ the makespan of any heuristic plan. The bounds give
$LB \le C^*_{\max} \le H$. Constraint propagation can *prove* infeasibility of a smaller $H$ (Section
5.3), e.g. $H = 7$ for instance B.

### 3.2 Decoding

A sample is decoded per operation: exactly one active variable gives its start, otherwise the sample is
rejected. Every decoded schedule is then checked by `Schedule.violations()` (`erpq/schedule.py`), a
checker that is independent of the QUBO encoding. It shares only the instance accessors `setup()` and
`fixed_conflict()` with the builder. Reported "feasible / optimal" fractions always come from this
checker, and objectives are compared with CP-SAT.

## 4. Assumptions and simplifications

* Integer hours. Durations are integers, so start times on an hourly grid lose nothing.
* Non-preemptive operations. A breakdown restarts the interrupted operation after the repair (Stage 2
  rolling model).
* Setups are *minimum gaps* between consecutive jobs on a unit (like CP-SAT transition times). They do
  not consume the operator and may overlap a maintenance window. The QUBO and CP-SAT enforce them
  pairwise, which equals the "consecutive only" reading when the triangle inequality holds; this is
  checked (`Instance.check_setup_triangle`). The first job on a machine needs no setup.
* Parallel units of a type are identical (same durations).
* Optimality of the QUBO is "within the horizon $H$". For pure makespan this is global since
  $H \ge C^*_{\max}$. For weighted objectives it is certified by the horizon certificate, or checked
  against CP-SAT without a horizon.

## 5. Qubit reduction (exact)

Every method below keeps **every** feasible schedule that fits the horizon, so the optimum is never
lost. At the two unpruned levels (`none`, `horizon`), start values that violate a *unary* constraint
(release date, maintenance window, machine-ready time, running operation) keep their qubit and get a
linear penalty $C$, so these QUBOs are exact for the extended model too
(`tests/test_qubo.py::test_unpruned_levels_exact_with_unary_constraints`). From `window` on, such
values are removed.

| 3x3 at $H = 8$ | qubits | quadratic terms | one-hot subspace | how |
|---|---|---|---|---|
| naive (all $t < H$) | **72** | 638 | $8^9 \approx 1.3\cdot10^8$ | challenge reference |
| fit the horizon ($t + p \le H$) | 67 | 556 | $6.9\cdot10^7$ | |
| start windows | **39** | 181 | 512,000 | challenge reference ("simple start-window pruning") |
| + arc consistency (AC-3) | 39 | 181 | 512,000 | |
| + singleton arc consistency (SAC) | **33** | 123 | 103,680 | Section 5.3 |
| + domain-wall encoding | **24** | (dense) | - | Section 5.5 |
| job-order code (comparison only) | **3** | 2 | - | Section 5.6; coefficients from brute force |

### 5.1 Start windows
$t \ge \text{head}(o)$ (release + predecessors) and $t \le H - \text{tail}(o)$ (own and successor
durations). Machine ready times, maintenance windows, and setups after running operations remove further
values. Gives 39 for instance B, the challenge's reference.

### 5.2 AC-3
Pairwise constraints (precedence, capacity with setups) are kept as Boolean compatibility matrices. A
start value without a compatible value in some neighbour's domain is removed, and this repeats until
nothing changes. *Exact:* such a value cannot appear in any feasible schedule.

### 5.3 Singleton arc consistency (SAC)
For each remaining value: fix it, run AC-3; if some domain becomes empty, the value is impossible and
is removed. Repeat to a fixpoint. This is polynomial ($O(\#\text{values}\cdot \text{AC-3})$) and exact for
the same reason. At a tight horizon it is very strong:

* instance B, $H = 8$: 39 $\to$ 33 qubits;
* instance A, $H = 4$: SAC alone fixes every start time, so the problem needs 0 qubits;
* SAC proves $H = 7$ infeasible for instance B, which certifies $C^*_{\max} = 8$ without any solver.

Operations whose domain shrinks to one value become constants. Arc consistency guarantees that they
are compatible with every remaining value, so they need neither a qubit nor a coupling.

### 5.4 Horizon ascent and certificate
Qubits grow by about 10-15 per extra hour of horizon (`results/extension/reduction.md`, "horizon
effect"). Horizon ascent (`erpq/horizon.py`) builds the SAC-pruned QUBO for $H = LB, LB+1, \dots$:

* if SAC proves $H$ infeasible: next $H$ (no solver call);
* otherwise solve; a found objective $V$ is final when $V \le$ bound$(H)$, where
  bound$(H) = a(H+1) + b \min_j \big[w_j (H+1-d_j)^+ + \sum_{i\ne j} w_i (LB_i - d_i)^+\big]$ is a lower
  bound on the cost of any schedule with $C_{\max} \ge H+1$ (the last job is at least $H+1-d_j$ late,
  every other job finishes no earlier than its own bound $LB_i$). For pure makespan the certificate
  holds as soon as a schedule is found.

### 5.5 Domain-wall encoding
A $d$-valued one-hot group ($d$ qubits) is re-encoded with $d - 1$ qubits $s_1..s_{d-1}$ ($s_0 = 1$,
$s_d = 0$) via $x_k = s_k - s_{k+1}$ (Chancellor 2019). Because $x_k$ is *linear* in $s$, every quadratic
term stays quadratic and the one-hot penalty vanishes identically ($\sum_k x_k = 1$). The only new
constraint is a single wall, $A_{dw}\sum_k (1 - s_k)s_{k+1}$. (`erpq/domainwall.py`)

*Correctness:* a broken wall creates $x$ values in $\{-1, 0, 1\}$. We bound the energy one broken wall
can gain by $R_{\max}$ (its non-negative linear coefficients plus its couplings to other groups, which
hold at most $\lfloor (d_h-1)/2 \rfloor + 1$ entries equal to $+1$) and set $A_{dw} = U + 1 + R_{\max}$.
For instance B (24 qubits) and instance A (8 qubits) we additionally **enumerate all $2^{n}$ states**:
every ground state is an optimal schedule (`run_baseline.py`, `tests/test_qubo.py`).

**Our smallest time-indexed QUBO for the baseline 3x3: 24 qubits** (vs 72 naive, 39 with windows). It
is polynomial to construct and certified correct by exhaustive enumeration of all $2^{24}$ states. We do
not claim that no smaller time-indexed QUBO exists. Fewer qubits overall are possible only by giving up
what makes this model useful; Section 5.6 shows the extreme.

### 5.6 Job-order code: fewest qubits, comparison only
`erpq/permutation.py`. In a same-route flow shop with $\le 3$ machines and pure makespan some
permutation schedule is optimal, so it is enough to choose the job order. The order is stored as a
binary code $k$ in $\lceil\log_2 n!\rceil$ qubits and decoded by list scheduling.

* Cost table: $f(k)$ is the makespan of order $k$ for $k < n!$; unused codes get $\max f + 1$, so they
  lie above every schedule.
* A Moebius transform gives the unique multilinear polynomial
  $f(x) = \sum_S c_S \prod_{i \in S} x_i$ with these values.
* Terms of degree $\ge 3$ are quadratised with Rosenberg auxiliaries $y = ab$, penalty
  $M_y(ab - 2ay - 2by + 3y)$ with
  $M_y = 1 + \sum_{T \ni y} |c_T| + 2\sum_{z \text{ built from } y} M_z$. Correcting the first
  inconsistent auxiliary (in creation order) always lowers the energy, so every ground state has
  consistent auxiliaries and decodes to an optimal order.

Instance B needs **3 qubits** and 2 couplings, $E = 8 + x_0 - x_0x_1 + 2x_1x_2$. The cubic coefficient
of its cost table is 0, so no auxiliary is needed (random 3-job flow shops need 3 or 4 qubits). All
$2^3$ states are enumerated: the 4 ground states are the 4 optimal job orders (makespan 8). Any code
that gives each of the 6 job orders its own basis state needs at least 3 qubits. Instance A needs 1
qubit. (`run_baseline.py`, `tests/test_permutation.py`)

Why it is not our formulation:
* its coefficients are the makespans of all $n!$ job orders, computed classically before the QUBO
  exists. Brute force has already solved the problem, and the quantum step only finds the answer again;
* the table has $n!$ entries and the polynomial degree grows to $\lceil\log_2 n!\rceil$, so the
  auxiliaries multiply (code qubits alone: 3, 5, 7, 10 for 3-6 jobs);
* the qubits hold only the job order; the start times come from a classical decoder;
* it is exact only where permutation schedules are dominant. `metaltech_monday` (a job-specific
  route, setups, maintenance, tardiness) is outside that, and the builder refuses it.

## 6. Solvers and how the quantum part works

### 6.1 Instance A: QAOA with the transverse-field mixer
12-qubit QUBO ($H = 5$, window/SAC pruning) → Ising $E = c + \sum_i h_i Z_i + \sum_{ij} J_{ij} Z_i Z_j$
→ QAOA circuit $|+\rangle^{\otimes n}$, then $p$ layers of $e^{-i\gamma_k E/\lambda}$ and
$e^{-i\beta_k\sum_q X_q}$ ($\lambda = \max|h|,|J|$, a normalisation that needs no knowledge of the
spectrum). The simulator is our own exact state vector in NumPy (`erpq/solvers/qaoa.py`), with
**adjoint gradients** (one forward and one backward sweep per gradient) and layer-wise L-BFGS-B:
$p=1$ from a grid plus random starts, then INTERP initialisation (Zhou et al. 2020) and linear-ramp
starts. The optimised circuit is rebuilt gate by gate in Qiskit (RZ, RZZ, RX) and simulated with
`qiskit.quantum_info.Statevector`; the distributions agree to $\sim10^{-16}$.

The best of 4,096 measured samples is the output schedule (makespan 4 = optimum, the same schedule as
the challenge's example). $P(\text{optimal})$ rises from 0.024% (1 of 4,096 states) for uniform sampling to about 10% at
$p=6$.

### 6.2 Instance B: XY-mixer QAOA simulated exactly in the feasible subspace
The 33-qubit QUBO has a $2^{33}$-amplitude state vector (137 GB), too large to simulate. We use the
Quantum Alternating Operator Ansatz (Hadfield et al. 2019): each operation's start qubits form a register
prepared in a W state, and the mixer $e^{-i\beta\sum_{(k,l)\in\text{ring}}(X_kX_l + Y_kY_l)/2}$ only
moves the single excitation inside a register. The Hamming weight of each register is conserved, so the
state never leaves the one-hot subspace of dimension $\prod_o d_o = 103{,}680$. Inside it, the mixer of
register $o$ is $e^{-i\beta A_o}$ with $A_o$ the ring adjacency matrix, and the cost is diagonal. This is
an **exact** simulation of the 33-qubit circuit, not an approximation. One-hot constraints are satisfied
by construction, so the cost landscape only contains precedence/capacity penalties and the objective.

The hardware form (`mixer="parity"`: ring split into layers of 2-qubit XX+YY gates) is also
implemented. It was cross-checked against a Qiskit circuit (StatePreparation of W states plus
`XXPlusYYGate`) embedded into the full $2^{n}$ space: maximum deviation $\sim10^{-16}$
(`tests/test_solvers.py`).

### 6.3 Classical QUBO solvers and VeloxQ
Simulated annealing and tabu search (`dwave-samplers`) solve the *full* QUBOs, including the one-hot
penalties, as a cross-check and for the algorithm comparison. `erpq/solvers/samplers.py:veloxq` submits
the same `BinaryQuadraticModel` to **VeloxQ** through the official `veloxq-sdk`. VeloxQ is
Quantumz.io's classical, GPU-based QUBO solver; the default backend is `VeloxQH100_1`, one H100.
* The call is `VeloxQSolver().sample(bqm, vartype="BINARY")`, with 1024 reads x 5000 steps.
* The SDK's default domain for in-memory problems is SPIN, so BINARY is requested explicitly. Any
  SPIN answer would be mapped back with x = (s + 1) / 2.
* States are mapped back by their (string) labels and the energies re-evaluated locally. Every sample
  is then decoded and validated like any other.
* It is enabled with `--veloxq` when `VELOX_TOKEN` is set. The service takes no seed, so reruns differ
  slightly.
* Timing: the service reports its own solver time, about 0.1 s per call here, and TTS99 in seconds
  uses it. The client wall time (7-15 s per call, mostly upload, queueing and download) is recorded
  separately.
* Cost: the service bills about 1 quota unit per millisecond of solver time. Solver time is set by
  reads x steps and grows only slowly with size (0.12 s for 3-72 qubits, 0.55 s for 726 qubits at
  1024 reads x 5000 steps), while every call pays a network round trip of a few seconds. This is why
  the decomposition (Sec. 6.5) packs 8 sub-QUBOs into one call.
* What we tried on large QUBOs (Part 6), one call each: 4x more steps, all coefficients divided by the
  largest one (same problem, different scale), and penalties x0.5 / x0.25. None had an effect larger
  than the spread between identical calls, except the lower penalties (8 jobs: 44 instead of 50), and
  those lose the exactness guarantee. The SDK's second solver (`SBMSolver`, simulated bifurcation) is
  not enabled for our account (HTTP 401).
* Where VeloxQ is weaker: on some residual QUBOs of rolling re-planning (31-39 qubits) its reads end in
  a local minimum above the ground state that SA escapes (Part 4: 33 / 36 scenarios optimal; 4x more
  steps did not help).
* VeloxQ is used in five places: the Stage-1 cross-checks (5 formulations of the 3x3), the Part-2
  comparison (4 formulations x 3 calls), the Part-4 live re-planning column, the Part-6 whole-QUBO
  calls and settings, and the Part-6 decomposition. All results, lessons and the cost are collected in
  [`VELOXQ.md`](VELOXQ.md).

### 6.4 Verification chain
1. Ground states certified: all $2^n$ states (n ≤ 26) or the one-hot subspace plus the penalty theorem.
2. Every sample decoded and checked by the independent validator.
3. Objective compared with CP-SAT (OR-Tools), which models the same constraints with interval variables.
4. Instance B and A: also brute force over permutations.
5. Simulators cross-checked against Qiskit circuits; gradients against finite differences.

### 6.5 Decomposition for large order books (`erpq/decompose.py`)
At the shift horizon the time-indexed QUBO of a whole order book grows fast (272 qubits for 8 jobs, 726
for 12). Neither SA nor VeloxQ then finds the optimum in one call. The decomposition is a
large-neighbourhood search whose every step is a small *exact* QUBO:

* **Neighbourhood.** Free k jobs (k = 6). Every operation of the other jobs stays where the current
  plan has it, as an `Instance.fixed` entry. A fixed entry blocks its unit including the setup gaps
  before and after it (`Instance.fixed_conflict`, the same semantics as a running operation in
  rolling re-planning, in the QUBO domains and in the validator).
* **Sub-QUBO.** Built with SAC pruning and the provable penalties U + 1. Its objective is the full
  objective up to a constant: `Schedule.makespan` and the lower bound both include the fixed
  operations, and the tardiness of a fixed job does not change. So, by the theorem of Sec. 3.1, its
  ground states are the best re-placements of the k jobs given the rest of the plan
  (`tests/test_decompose.py` checks the constant).
* **Feasibility.** The current placement of the freed jobs lies in the sub-QUBO's domains, so a
  sub-problem is never infeasible. A candidate is merged into the plan and accepted only if the merged
  plan passes the validator of the *original* instance and is not worse. The plan therefore never gets
  worse and never leaves the horizon.
* **Batching for a cloud solver.** Each round draws 8 neighbourhoods of the current plan. For VeloxQ
  they are stacked into one block-diagonal QUBO (disjoint variables, no couplings between blocks), so
  one call solves all 8. The best read is taken per block, which is valid because the blocks are
  independent. SA solves the same 8 sub-QUBOs one after another. The candidates are tried best first,
  each merged into the plan as it is at that moment and validated again.
* **Not a proof.** The search finds good plans, not certificates. Optimality is judged against CP-SAT
  with the same horizon. The search stops early when it reaches that value, only to save calls.

### 6.6 Instance B on 4 qubits: Pauli correlation encoding (`erpq/solvers/pce.py`)
A QUBO whose qubits hold the start times cannot get near 4 qubits. After SAC, instance B still has
103,680 start-time combinations, and telling them apart takes at least $\lceil\log_2 103{,}680\rceil = 17$
bits. Only 13 of them are feasible, which 4 bits could number, but listing them means solving the
problem first. Fewer qubits therefore need a different way of holding the variables:
* the job order only, with brute-force coefficients (Sec. 5.6, 3 qubits);
* or the correlators of a small state, which is this section.

The certified 24-variable domain-wall QUBO (Sec. 5.5) is solved on 4 qubits with Pauli correlation
encoding (PCE; Sciorilli et al., arXiv:2401.09421). The QUBO is unchanged; only the way a quantum state
holds its variables changes.

* **Encoding.** Variable $i$ is the sign of $\langle\Pi_i\rangle$ on one 4-qubit state,
  $x_i = (1 - \mathrm{sgn}\langle\Pi_i\rangle)/2$. The $\Pi_i$ are the weight-2 and weight-1 Pauli
  strings of the families $Z\cdots Z$, $X\cdots X$ and $Y\cdots Y$, $3\,(\binom{4}{2} + 4) = 30 \ge 24$ of
  them. Strings of one family commute, so one evaluation needs 3 measurement settings. With 3 qubits,
  these families have only $3 \cdot 7 = 21 < 24$ strings.
* **Training.** Hardware-efficient ansatz: RY, RZ on every qubit, then 4 x (CNOT ring, RY, RZ), 40 angles.
  The loss is the paper's relaxation of the Ising energy,
  $L = c + \sum_i h_i t_i + \sum_{i<j} J_{ij} t_i t_j + \beta\nu\big(\tfrac{1}{m}\sum_i t_i^2\big)^2$ with
  $t_i = \tanh(\alpha\langle\Pi_i\rangle)$. As in the paper, $\alpha = n^{\lfloor k/2 \rfloor} = 4$ and
  $\beta = 1/2$; $\nu = (\sum|h| + \sum|J|)/2$ takes the place of its MaxCut bound. L-BFGS-B uses exact
  parameter-shift gradients, over independent random restarts.
* **Read-out and checks.** Signs give bits. The bits are decoded through the domain wall, checked by the
  validator and compared with CP-SAT. The correlators are cross-checked against a Qiskit gate-level
  circuit, and the read-out is repeated from shots in the 3 settings.
* **Result** (`results/extension/pce.md`, 100 restarts). Optimal schedule in 19% of the restarts, and
  44% after the paper's single bit-swap pass (classical post-processing); 22 restarts give 99%.
* **What it is not.**
  - A certificate: PCE is a variational heuristic, and certification stays with the 24-variable QUBO.
  - 24 independent qubits: the 4 qubits hold 24 correlators.
  - An advantage: a 4-qubit circuit is classically simulable. The same loss over 24 free parameters,
    with no quantum state, also reaches 19%, and SA reaches 95% per read. Part 7 shows the qubit count,
    nothing more.

## 7. Stage 2: what is extended and why

The extension is one integrated model, **`metaltech_monday`**: the 3x3 order plus an urgent repair
part Z4 with its own route (F then T, no welding), two part families with 1 h changeovers on F and S,
planned maintenance of S in [5, 6), due dates and customer weights. The objective is
$2C_{\max} + \sum w_j T_j$. Built step by step (the feature ladder), it answers the challenge's
directions on *this* model:

1. **Price of realism and qubit reduction** (`results/extension/reduction.md`): qubits per feature in
   the naive formulation vs ours (windows → SAC → domain wall), all certified exact.
2. **Algorithm comparison** (`algorithms.md`): XY-QAOA with ring/clique/parity mixers, expectation vs
   CVaR loss, parameter transfer from the 3x3, versus SA, tabu and VeloxQ (live) on four formulations
   (naive, windows, SAC, SAC+domain wall), with seeds or repeated calls, 95% confidence intervals and
   time-to-solution. Includes a penalty-weight sweep.
3. **Scaling and variance** (`scaling.md`): random extended instances with 2-6 jobs, several instances
   and seeds per size. Shows qubits vs size and solver success vs qubits.
4. **Disruptions and rolling planning** (`disruption.md`): breakdowns during the shift, residual problems
   re-planned as small QUBOs (XY-QAOA with *transferred, fixed* angles where the subspace can be
   simulated, SA otherwise, or SA throughout, or live VeloxQ calls) vs the ERP's
   right-shift repair vs CP-SAT.
5. **Functional scaling: a second milling machine** (`investment.md`): Monte-Carlo over order books with
   one vs two milling machines, savings and payback under explicit (CLI-configurable) cost assumptions,
   plus the qubit price of the extra unit.
6. **VeloxQ at scale** (`veloxq.md`, needs the token): random order books with 4-12 jobs (77-726
   qubits). One VeloxQ call on the whole QUBO, the solver settings that could help, and the
   decomposition of Sec. 6.5 with 8 sub-QUBOs per VeloxQ call, each against SA and CP-SAT.

## 9. Alternatives considered and rejected

* **Plain transverse-field QAOA for instance B.** It needs $2^{33}$ (or $2^{24}$ with domain walls)
  amplitudes, and spends most amplitude on states that violate the one-hot constraint. The XY mixer
  removes that subspace exactly.
* **Binary (log) encoding of start times.** $\lceil\log_2 d\rceil$ qubits per operation, but the
  pairwise constraints become higher-order polynomials that need auxiliary qubits to quadratise. It was
  not pursued: the domain-wall encoding already removes one qubit per operation and keeps every term
  quadratic, without auxiliaries.
* **Permutation encodings as the model.** Position-based: $n^2$ qubits, but the makespan of a
  permutation is a max-plus expression, not quadratic. An exact quadratic form needs the full $n!$
  cost table, so the problem is solved while building the QUBO. The binary job-order code
  (Section 5.6) takes this route to its extreme, 3 qubits for instance B, and is kept as a comparison
  only. Surrogates (TSP-like adjacency costs) lose exactness and cannot express setups together with
  outages, release dates or job shops.
* **Slack variables for inequalities.** The time-indexed model needs none: every constraint is a
  forbidden pair of start times.
* **Large penalties "to be safe".** These compress the objective scale and lower SA/QAOA success
  (penalty sweep). We use the provably sufficient $U + 1$ instead.
